# 12. Engineering: stack, capability map, middleware, contributor docs

Back to [index](../spec.md). Reader: implementers and contributors of
the product repo; the planner selecting work by module id. Type:
reference, with the contributor docs as outlines.

## 12.1 Tech stack

| Component | Language | Notes |
|---|---|---|
| `romeu` (`cmd/romeu`) | Go (version pinned in `mise.toml`) | host build; darwin amd64/arm64; linux builds only for CI tests |
| `julieta` (`cmd/julieta`) | Go | sandbox build; linux amd64/arm64 |
| shared packages (`internal/...`) | Go | see the capability map |

| host probe harness (`e2e/probes`) | Go | runs probe steps, writes `probe-result.v1` JSON |

| skills (`skills/*/SKILL.md`) | Markdown | Claude Code skills |

| data | YAML (specs, catalog, ask-first list), JSON (state, results), TOML (mise, read only) | |

Go dependencies (each an ask-first addition; complete v1 list):
`go.yaml.in/yaml/v3`, `github.com/BurntSushi/toml`,
`github.com/santhosh-tekuri/jsonschema/v6` (validates examples against
the generated schemas), `golang.org/x/term`, `golang.org/x/sys`. No CLI
framework (stdlib `flag`); TTY tests use a `/dev/ptmx` helper built on
`x/sys/unix` (no pty library); OCI manifest reads use stdlib `net/http`;
the ssh-agent identity listing is implemented in `internal/signing`;
JSON Schemas are generated by the in-repo `tools/schemagen`. CI tools
(not Go deps): `golangci-lint`, `govulncheck`, `reuse` (all pinned in
`mise.lock`). *Why for us:* two binaries with ~15 and ~25 commands do
not need cobra, and fewer dependencies shrink the host trust surface.

External tools at runtime: `sbx` (host, >= v0.46.0), `git` (host and
sandbox, floor in [05](05-security.md#51-hardened-git-internalgitsafe)),
`mise` and `herdr` (sandbox, pinned by version and sha256).

## 12.2 Development commands and capability map

```
Scaffold:   go run ./tools/new {adr|invariant|probe|kit|command|lesson} <name>
Generate:   go generate ./...
Build:      go build ./...
Test:       go test -race ./...
Golden:     go test ./internal/render/... -update   # local only; CI rejects -update and lists changed goldens
E2E (CI):   go test -tags e2e ./e2e/...             # git + docker + fake sbx; no real sbx
E2E (host): go test -tags host -json ./e2e/host/... # maintainer machine only; real sbx
Fast:       go run ./tools/ci fast                  # what the pre-push hook runs
All checks: go run ./tools/ci all                   # exactly what CI runs
Probes:     go run ./e2e/probes --block A --out docs/probes/
Release:    go run ./tools/release --version v1.0.0 --dry-run
```

Module ids are stable; the plan selects work by them.

| Module id | Responsibility | Depends on |
|---|---|---|

| `probes` | probe harness (pure core + exec layer), `probe-result.v1`, redacted sbx recordings, `tools/ci probes` lifecycle | - |

| `termsafe` | escaping of control, bidi, zero-width and tag characters; the default-escaping CLI writer | - |
| `gitsafe` | every git invocation: hardened env and flags, allowlisted ref namespaces, create-only refs, bundle verify/unbundle, fsck and tree walk for materialization | - |
| `catalog` | embedded egress catalog and lookups | spec |
| `oci` | read and verify a workload or kit descriptor by digest; strict descriptor grammar | spec |
| `signing` | ssh-agent identity listing for the `git-ssh-sign` rule | - |
| `state` | host state records, the candidate and generation state machines, descriptor cache, toolchain acknowledgement, flock | spec, canon |
| `egress` | derive egress from `mise.lock` at pinned SHAs; split auto vs gated | catalog, gitsafe, canon |
| `render` | render candidates (`sbxenv.yaml`, workspace files, `render.json`), materialize kits via `os.Root`, promotion commit and recovery | spec, egress, oci, gitsafe, state |

| `memstore` | memory Store interface, `fs` backend on `os.Root`, layout allowlist, JSONL import/verify | spec, canon |
| `julieta-core` | setup, repos, install/lock (mise), hooks and recorded failures, status, spec and catalog validation, version and compatibility | spec, gitsafe, catalog |

| `handoff` | handoff write/show/list, the handoff reader, SessionStart output | memstore, gitsafe |

Build order: `ci-bootstrap`, `probes` -> probe block A (maintainer, in
parallel with) `canon`, `spec`, `termsafe`, `gitsafe`, `signing` ->
`catalog`, `oci`, `state`, `sbxdrv`, `memstore` -> `egress` -> `render`
-> `gate` -> `romeu-cli` (init, sync, approve, status, doctor, adopt) ->
`julieta-core`, `layout` -> `handoff`, `salvage` -> `romeu-cli` (run,
stop, salvage, rm, recreate, retire, pull, handoff) -> `kits`, `skills`
-> `ci-release` -> block B (acceptance on real hosts) -> `docs` ->
`tools/ci acceptance`. Block A settles every sbx fact the code depends
on before `sbxdrv` and `render` are finalized; block B only accepts
built artifacts. Residual rework risk: a block B failure of a built kit
is fixed in the kit, not in the architecture (see
[11](11-host-probes.md)).

## 12.3 Generators

Every rule with more than one consumer has one source; the consumers are
generated and `tools/ci generated` fails when `go generate ./...` leaves
a diff. Nobody hand-edits a generated file.

| Source | Generated consumers |
|---|---|
| spec struct tags (`gate`, `apply`) | widening set and recreate digest field lists, the I7 flip-table test, the field table in `docs/reference/project.md` |
| `internal/spec/rules.go` + Go types | validators, the rule table in the reference docs, `schemas/*.json` (`tools/schemagen`) |
| `internal/cli` error table | `--help` exit-code sections, `docs/reference/errors.md`, `docs/reference/exit-codes.md` |
| command definitions | `docs/reference/<command>.md` |
| `internal/state` transition tables | state-machine tests; the diagrams in `ARCHITECTURE.md` |
| `.github/ask-first.yaml` | `.github/CODEOWNERS`, `docs/reference/ask-first.md`, the `mutate` trigger |
| the vocabulary table (01 1.7) | the `tools/ci vocabulary` denylist |

`go run ./tools/new <kind> <name>` scaffolds with the next free id:

| Kind | Creates |
|---|---|
| `adr` | `docs/adr/NNNN-<name>.md` with the ADR sections (12.5) |
| `invariant` | the next `I<n>`: a guard stub and a failing test, both tagged, and the table row to fill |
| `probe` | a probe definition with `expect`, decision table and `affects` to fill |
| `kit` | `kits/<name>/` with a descriptor on the pinned frontend |
| `command` | the command stub, its help test and its reference entry |
| `lesson` | a `docs/lessons.md` entry with the required fields |

## 12.4 Middleware before and after every change

The before/after question "what check or generator would have caught
or produced this, and does it exist now?" is answered mechanically:

| When | Mechanism | Enforces |
|---|---|---|
| before push | tracked `.githooks/pre-push` runs `go run ./tools/ci fast` (contributors enable it with `git config core.hooksPath .githooks`; inside a sandbox, julieta's dispatcher runs it automatically) | format, vet, lint, unit tests, generated files, hygiene, sequences, vocabulary |
| every PR | `go run ./tools/ci all` in CI | the full list in [10 10.2](10-testing-style.md#102-ci) |
| every PR | `tools/ci pr` reads the pull request event payload | the body has non-empty **Why**, **What changed**, **Evidence** and **Lessons** sections; a **Middleware** line of the form `check: <tools/ci subcommand or test>`, `generator: <tools/new kind or go:generate source>`, or `none: <reason>`; every changed golden listed under Evidence; a quoted maintainer approval when the diff touches a path in `.github/ask-first.yaml` |
| merge | branch protection | CI green; code-owner review for ask-first paths |

## 12.5 Decisions and history

- The spec (`docs/spec.md`, `docs/spec/`) describes the current state
  only. Review history lives in `docs/reviews/round-<n>.md`.
- Decisions live in ADRs under `docs/adr/` (adr-tools layout,
  `.adr-dir` -> `docs/adr`), one decision per record, file
  `NNNN-<title>.md`, sections Status, Date, Context, Decision,
  Alternatives considered, Consequences. Status moves Proposed ->
  Accepted -> Superseded by NNNN or Deprecated.
- An accepted ADR is never rewritten. A spec change that reverses a
  decision adds a new ADR with `Supersedes: NNNN`, and the old ADR gains
  only its status line `Superseded by NNNN`. `tools/ci sequences` checks
  both links.
- A settled open question becomes an ADR; the `docs` module writes the
  initial set from this spec's decisions (listed in
  [reviews/round-2.md](../reviews/round-2.md#settled-questions)).

## 12.6 Release notes

`tools/release notes` generates the notes from the Conventional Commit
subjects since the last tag, grouped by type, with each merged PR's
**Why** section; a PR that changes a file format version or an exit code
is listed first. Nobody writes release notes by hand.

## 12.7 Text standard and lessons

- Commits: Conventional Commits; the body says why and cites evidence
  where a claim can be checked; no filler, no boilerplate footers;
  English; no em dash.
- PRs and issues: the PR template sections Why / What changed / Evidence
  / Middleware / Lessons, checked by `tools/ci pr`.
- `docs/lessons.md`: one entry per lesson (date, what happened, the
  rule, and the enforcing `tools/ci` subcommand or test name, or "no
  check possible: <reason>"), checked by `tools/ci lessons`; a lesson
  that can become a deterministic check becomes one in the same PR.

## 12.8 Contributor docs (outlines)

Every document in the repo follows one documentation standard, stated
in `CONTRIBUTING.md`:

- each page names its reader and the task it serves, and has one content
  type (tutorial, how-to, reference or explanation);
- headings describe what the section answers;
- each section stands on its own when read alone, by a person or an AI
  agent; terms, acronyms, trust boundaries and prerequisites are
  defined before they are used, and each concept has one name (01 1.7);
- examples are complete and copyable, with expected output where it
  helps;
- prose is concise and active; no marketing language, no em dash;
- decisions go in ADRs (12.5), never in page prose that later rots.

| File | Reader and type | Outline |
|---|---|---|
| `README.md` | a developer deciding whether to use the product; explanation + quick start | what it is and who it is for; when not to use it; prerequisites (macOS host, sbx, git floor); install and verify (checksums, attestation); first run (J1 in six commands); the trust model in one paragraph with a link to `ARCHITECTURE.md`; links to guides and reference |
| `ARCHITECTURE.md` | a contributor or reviewer; explanation, one page | components and their single jobs; the trust boundaries A-F; the gates; the state machines (candidate, promotion commit, generation, probe) as generated diagrams; where each invariant is enforced; module dependency direction |
| `CONTRIBUTING.md` | a contributor; how-to | the dev loop (`tools/new`, `go generate`, `tools/ci fast`, `tools/ci all`); enabling the pre-push hook; how to add a command, invariant, probe or kit; what counts as ask-first and how approval is recorded; the PR template and the Middleware line; the text standard; the documentation standard above; ADRs and superseding |
| `docs/guide/*` | the operator; how-to, one page per journey | the steps of the journey in [09](09-journeys.md) with expected output and recovery from each expected error id |
| `docs/reference/*` | anyone looking up a fact; reference, generated | commands, file formats, errors, exit codes, ask-first surfaces |
